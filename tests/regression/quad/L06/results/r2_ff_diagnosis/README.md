# R2 FF-on diagnosis: the scripts, inputs and outputs behind decision 0014 W4

The evidence for the R2 FF-on diagnosis in `docs/decisions/0014-l6-stage-c-d-term-and-feed-forward.md` (W4, "Diagnosis")
and for the harness fix `docs/decisions/0016` (the plugin's first gyro read returns the starting rates). Owner ruling,
2026-10-03: "0011 style" (`docs/decisions/0011-t3-reference-storage.md`): the scripts, the tool source, the small inputs
and the summary outputs are committed; the large traces and the gz logs are pinned by `SHA256SUMS` and regenerated.

**Pre-0016 behaviour.** The gz input logs were flown before decision 0016, when the plugin fed the gyro chain the raw gz
read (zero rates) at step 0. `regenerate.sh` reproduces them with the test-only switch
`MARV_GZ_TEST_ZERO_FIRST_READ=1` (`sim/gz/plugin/src/lockstep.cpp`), which restores that read exactly. Without the
switch the logs differ from these. The `first_read_zero 1` / `0` line of each `sim_in_*.txt` is the tool-side form of the
same choice (1 = the harness's zero read, 0 = the starting rates fed).

## What it claims, and the output that backs each claim

All counts are R2 (`recover_tumble`), FF on (`rate_ff_enable` = 1), envelope A, m = 1, 20293 attitude executions;
"viol" = violations over the six channels.

1. **The gz step-0 zero read is the main cause and the tool reproduces gz.** gz FF on: w_y +1.9881 at execution 262
   (`b_ladder_A_B.txt:3`). Firmware path with the zero read (`A_qg_z1_ff`): w_y +1.9949, max |sim - gz| 0.0158 rad/s
   (`b_ladder_A_B.txt:4`; decision: "0.016 rad/s"). The logged execution 0 has gyro 0 and execution 1 has ω0
   (`a_replay.txt:3-4`).
2. **Without the zero read: about 2416 violations, worst w_z +0.24, attitude inside the envelope.** `B_qg_z0_ff`: w_x 334 +
   w_y 329 + w_z 1753 = 2416 violations, w_z +0.2404, err_x/y/z all negative (`b_ladder_A_B.txt:5`). The PI-only loop is
   unaffected by the read; the D term and the FF lag term differentiate the step (decision text; the ladder `I`/`J` rows,
   FF off, `b_ladder_C_D_E_F_G_H_I_J_K_M.txt:10-11`).
3. **Second cause: yaw saturation and the yaw integrator freeze.** Without the zero read the allocator flags yaw at 93
   executions (`flags [0, 0, 93]`, `b_ladder_A_B.txt:5`; 1 to 93 in the decision). Removing the allocator limit
   (`rotor_speed_max` 6000): 1178 violations, w_x +0.0309, w_z +0.0657, flags [0, 0, 0] (`h_more.txt:2`, `D2_cont_bigfmax`).
4. **What remains: T_ff and the rotor-speed lag against the design's torque lag.** `H2_cont_ideal_bigfmax` (ideal FF, no
   saturation, no zero read): w_z +0.0086, 423 violations (`h_more2.txt:1`) against F + Q 0.00792
   (`b_ladder_A_B.txt:1`). INFERRED, one nominal run. Design-model forms of the FF in `d_c8fw_*.txt`: `ideal`, `zoh`, `fw0`
   0 violations, `fw` 141, w_z +0.0015 (`d_c8fw_ideal.txt`, `d_c8fw_zoh.txt`, `d_c8fw_fw0.txt`, `d_c8fw_fw.txt`); with the zero
   read 14461 (`d_c8fw_ideal+zr.txt`) and 19197 (`d_c8fw_fw+zr.txt`); no FF 13438 (`d_c8fw_none.txt`). Sensitivity in `e_sens.txt`.
5. **Ruled out: a centred collective.** `A_centred_z1` 11562 violations (`h_more.txt:7`), `B_centred_c` 4244 (`h_more.txt:4`).
   Motor 1 at its floor: the replay shows motor 1 at 48 for 326 executions (`a_replay.txt:8-9`), which the allocator's own
   collective choice sets (decision text, not a separate output).
6. Other ladder rows (K, M, the lag plants E-G, T_ff = 0) are in `b_ladder_*.txt`, `h_more*.txt`; `c_wz.txt` compares the
   tool's design plant with the design model's nominal member.

- Committed, small: `common.py`, `a_replay.py`, `b_ladder.py`, `c_wz.py`, `d_c8fw.py`, `e_sens.py`, `h_more.py`,
  `h_more2.py` (the scripts), `tool2.cpp` and `build2.sh` (the tool: `recovery_cause_tool` plus the scratch modes),
  `sim_in_*.txt` (the tool's inputs, generated by the scripts and checked byte for byte), `a_replay.txt`, `b_ladder_*.txt`,
  `c_wz.txt`, `d_c8fw_*.txt`, `e_sens.txt`, `h_more.txt`, `h_more2.txt` (the summary outputs), `regenerate.sh`.
- Pinned by `SHA256SUMS` (paths relative to the work dir), not committed: the 27 `sim_*.txt` traces, `replay_in.txt`,
  `replay_out.txt`, `replay_rows_{on,off}.txt` (about 200 MB together), and the four gz `.bin` logs
  (`gz/recover_tumble_ff_{off,on}_run/*_m{1,2}_seed1.bin`; the scripts read on m1, on m2 and off m1, off m2 is pinned too).
  The hashes are those of the original files from the diagnosis session. The `.sdf` files are not pinned: each holds its
  own `log_path`. `design_r2.pkl` is derived by `b_ladder.py` and not pinned.
- Left out: `f_doff.py` and `g_udiff.py` (stdout-only probes of the design-off run; no committed output depends on them).

Work dir and gz-log dir: `MARV_R2FF_WORK` (the scripts' work dir, required) and `MARV_R2FF_GZ` (default `$MARV_R2FF_WORK/gz`).

## Regenerate and check (not in CI)

    tests/regression/quad/L06/results/r2_ff_diagnosis/regenerate.sh <work dir>

Needs `uv sync --frozen` and gz-sim 8. Every build and script comes from a detached `git worktree` of the pinned commit
(`PIN` at the top of `regenerate.sh`: decision 0016's commit 4a76755, where this record was produced and verified), removed
at exit, so the pre-0016 outputs stay reproducible after the firmware changes (the diffuser of decision 0017 is live in
the current tree); the scripts run are the record's own copies in that worktree. In it the script configures and builds
host-gz-l5, ensures the L5 T3 reference, runs `capture_gz.py --case r2` with the switch (gz logs kept in `<work dir>/gz`), builds the two tools, reruns
every script, then checks every `SHA256SUMS` line and the small files with `cmp`. It exits nonzero on any mismatch and
refuses to start if `<work dir>/gz` exists (`MARV_R2FF_REUSE_GZ=1` reuses it). Measured: 186 s wall (3 min 6 s; a first run took 189 s) on 16
cores, 0 mismatches (all 35 hashes and every committed small file reproduced bit for bit).
