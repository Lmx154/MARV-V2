# GX-14 BUILD: evidence

- `light/`: the Playwright JSON report and screenshots of the light e2e (`tools/gs/e2e.sh`, all specs; `gcs/e2e/build.spec.ts` is the Build panel's, with the fake cmake and ninja of `tools/gs/e2e_fake_build.py`).
- `real_build.py`: drives the real helper with the commands the Build panel sends, for one real host-gz-quadfc build under the heavy lock; its outputs (status before and after, events, the library entry with its describe string, the helper's build log) are in this directory when the run has been committed.

Real build (`real_build.py`, second run; the first run's evidence was overwritten by it): `status_before.json`, `build_reply.json`, `events.jsonl` (start, the number of progress events, done; the cmake and ninja text is left out because the GS-3 word scan of the repository flags the output, which names the link targets), `heavy_lock_during.txt` (the holder line, `cmd=GCS build host-gz-quadfc`), `library_entry.json` (every SIL image of the tree carries `build.describe`; the quad_fc one is `marv_sil_quad_fc`), `status_after.json`.

Finding: the dry run after a finished build says "2 steps", not "up to date". `ninja_dry_run_after.txt` shows why: the two steps are CMake's `Re-checking globbed directories` and `Re-running CMake` (CONFIGURE_DEPENDS globs). The glob check is a phony edge with no inputs (`VerifyGlobs.cmake_force`), always dirty to `ninja -n`, which cannot run it to see that its outputs did not change. So `ninja -n` alone never gives "up to date" on these trees. Resolved by the lead's decision: `parse_dry_run` (tools/gs/build.py) does not count those two steps, matched by their exact ninja descriptions, and reports `up to date` with `glob_recheck: true`, which the panel shows as `up to date (CMake re-checks its globs at build)`. `status_after.json` was recorded before that change and shows ninja's literal "2 steps"; `tests/tools/test_gs_build.py` parses `ninja_dry_run_after.txt` to "up to date".
